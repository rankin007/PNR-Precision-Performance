## Architecture

```text
Browser form
  -> POST /api/enquiries
     -> body/origin/honeypot/consent validation
     -> HMAC abuse bucket + idempotency reservation
     -> service-role-only Supabase insert (90-day expiry)
     -> existing encrypted SMTP notification
     -> generic stored receipt + opaque reference

Internal authenticated maintenance
  -> claim definite retryable notifications safely
  -> never retry delivery_unknown
  -> purge expired enquiries/buckets
  -> inspect/delete exact synthetic reference using sanitized status/counts
```

Supabase is the durable enquiry source of truth. The browser form state is transient. The API normalizes and validates it, derives only an HMAC abuse/idempotency value, stores the governed record and converts delivery outcomes into a finite sanitized status. SMTP is a notification sink, never the source of truth. The opaque reference connects visitor receipt, operator requests and sanitized proof without exposing database IDs or personal fields.

### 3. Origin-to-sink and failure paths

Origin: seven public form values, unchecked acknowledgement, honeypot and client UUID. ### 5. Discriminating examples

- Two concurrent posts with the same client UUID must produce one row, one reference and at most one notification; two rows or two accepted envelopes fails.

- An `Origin` for another host, a filled honeypot, an unknown JSON key or horse volume `0` must store/send nothing and reveal no rejection detail useful to abuse.
