## Flight evidence

### 1. Class and reason

`critical`: authentication, protected environment injection, privacy-sensitive denial proof, Production bindings, one deployment and five live alias writes are in scope.

### 2. Acceptance invariant at risk

One exact retained trainer with active membership and `horse.records.write` may render only its RLS-accessible horse/workflow. A generated absent/non-owned horse must render the same generic unavailable state without protected horse/stable/state/count data. Sign-out must remove the usable session, and signed-out/anonymous portal access must redirect to sign-in. Corrected bindings/candidate remain live only if the full invariant passes; otherwise complete compensation restores the known-safe state.

- Caller-generated UUID -> `/portal/horses/[horseId]` route parameter.
- `app/(portal)/layout.tsx` -> `requirePortalAppContext` for authenticated portal access.

- Vercel binding transaction -> process-only Supabase target -> exact retained graph -> one candidate -> five aliases -> automatic rollback/restoration.

### 4. Source of truth, transformations and sink

Supabase RLS and the retained 035K ownership ledger are the data/access truth. The exact retained Auth ID plus email hash selects one identity; exact-owned application rows produce membership and permission; SSR verification creates an in-memory cookie; RLS filters requested horse queries. The user-supplied route UUID may be serialized by Next.js, but only database-derived horse/stable/state/count material is protected leakage. The visible generic denial, sign-in redirect and sanitized verifier result are the acceptance sinks.

### 5. Discriminating examples

1. Generic denial plus the generated requested UUID only in route transport must pass. The former plausible implementation failed merely because the caller's own UUID appeared.
2. Generic denial plus retained horse name, retained stable name, `Status:` or `Count:` must fail. A weak verifier that only checks the title would wrongly pass.
3. A fake adapter that grants/returns the generated wrong horse must fail before acceptance. An absent-row-only fixture would not distinguish a broken authorization grant.
4. A sign-out adapter that retains a cookie, or an anonymous adapter that returns the dashboard instead of a sign-in redirect, must fail. Checking only the sign-out API return would miss usable-session persistence.
5. A partial binding write or alias mismatch must restore the entire known-safe set. Checking only the last write would miss split Production state.
