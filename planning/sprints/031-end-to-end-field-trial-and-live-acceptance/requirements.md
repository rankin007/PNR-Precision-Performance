## Outcome

Prove the integrated Precision Performance trainer workflow end to end in one governed non-production Preview using controlled synthetic fixtures, authenticated roles and representative mobile/desktop interaction. Reconcile functional, permission, privacy, accessibility, failure, cleanup and restoration evidence into one honest launch-readiness recommendation.

- capabilities that pass authenticated rendered/runtime proof;
- intentional fail-closed limitations that are correctly presented;

### Synthetic-only fixtures

Use no real horse, stable, trainer, owner, customer, patient, payment, email-content or clinical data. Fixtures must be visibly synthetic and contain no copied names, documents, photos, notes or measurements from real operations.

Use a fresh run ID and an in-memory/external protected ownership ledger. Declare ceilings before creation. The bounded default is:

- one synthetic stable;
- three synthetic horses representing complete, incomplete and unavailable/empty states;
- one administrator, one record writer and one read-only member test identity, plus anonymous/inactive/revoked states derived safely where the existing harness permits;
- the minimum synthetic measurements, notes, comments and evidence objects required by the matrix;
- zero commerce/customer/order/payment fixtures.

Builder may lower these ceilings. Any increase requires documented necessity within the same synthetic categories and must remain bounded. Auth identities are cleaned last.

Protected values, mailbox identifiers, passwords, OTPs, links, tokens, cookies, session data, service credentials and full provider identifiers must remain in protected process/browser memory and never appear in arguments, clipboard instructions, screenshots, logs, durable files or conversation.

Create `docs/END_TO_END_FIELD_TRIAL_AND_LIVE_ACCEPTANCE_031.md` before execution. It must define actor, device/viewport, precondition, action, expected UI, expected persisted state, denial/failure expectation, evidence method, cleanup owner and result for every case.

### 1. Authentication and access lifecycle

Prove:

- anonymous protected-route redirect;
- active authenticated portal bootstrap;
- administrator, record-writer and read-only access under existing permission codes;
- assigned/access-authorized horse visibility and wrong-horse/cross-stable denial;
- inactive/non-member or safely equivalent denial;
- session revocation and post-revocation denial;
- no inaccessible horse/stable influence on dashboard rows, counts, ordering or actions.

Do not change roles, permissions, memberships, assignments or RLS contracts except temporary exact-owned fixture assignments already supported by current schema/actions.

### 2. Mobile capture, review and persistence

At representative phone width and desktop width, prove:

- horse selection and date/time context;
- five raw measurements mapping to four lookup inputs;
- validation, review, correction, pending/retry and duplicate-submit prevention;
- typed note entry, mandatory review confirmation for non-empty notes and edit-invalidates-confirmation behaviour;
- device-keyboard dictation guidance without claiming application audio capture;
- submission persistence and exact horse/user association;
- safe unavailable results where production authority is incomplete;
- keyboard/focus/status/error behaviour and no horizontal overflow.

No under-60-second claim may be made. Timing may be measured as observational evidence with setup, device class, network condition and sample size recorded.

### 3. Results, history, trends and recommendations

Prove:

- current structured result and safe unavailable classification/recommendation language;
- stored formula/source/version context;
- historical snapshot stability;
- literal change only across compatible versions;
- incompatible/missing history treatment;
- trend/history navigation and accessible non-chart alternative where implemented;
- no fixture thresholds, biological interpretation, treatment or recommendation activation.

### 4. Stable dashboard and horse workspace

Prove:

- bounded stable overview and coherent horse workspace;
- complete, incomplete and unavailable/empty horse states;
- deterministic incomplete reason and permission-aware next action;
- neutral ordering and explicit clinical-priority unavailability;
- authorized action entry points and read-only suppression;
- 100-horse/200-test bounds remain explicit and no unauthorized aggregation occurs.
