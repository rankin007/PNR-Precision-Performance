# Sprint 020G - Clean Supabase Project Rebuild And Cutover Requirements

## Role And Profile

Builder executes this follow-up under the `strict` workflow profile and implements only from this applied sprint folder.

## Goal

Create a separate clean Supabase project from the current repository source of truth, establish a genuine migration ledger, recreate only current required hosted configuration and secrets, validate security and application behavior, cut the application over with a tested rollback path, and retain the old project unchanged as temporary rollback evidence.

## Accepted User Decisions

The user accepted all Sprint 020F recommendations:

- create a new Supabase project rather than rebuilding the linked legacy project in place
- preserve no legacy public-table rows
- preserve no existing Supabase Auth users, identities, MFA state, or sessions
- preserve no existing Storage buckets, objects, or metadata
- retire all seven remote-only public surfaces and migrate none of their data
- recreate only hosted configuration and secrets required by the current application
- establish fresh migration history by applying repository migrations to the new empty project
- retire legacy security findings with legacy objects, review/restrict current helper execution, and enable leaked-password protection
- use a controlled maintenance/cutover with immediate smoke tests and keep the old project available for rollback until later decommissioning

The seven retired remote-only surfaces are:

- `public."Test User"`
- `public."Test User_id_seq"`
- `public.client_applications`
- `public.etrakka_sessions`
- `public.etrakka_biochem_comparison`
- `public.horse_biochemistry_results`
- `public.horse_gallery_items`

Do not export, migrate, recreate, or copy data from those surfaces.

## Relationship To Earlier 020 Sprints

- Sprint 020F is complete and is the authority for the remote/repository comparison, preservation decisions, security findings, and exact cleanup proof.
- Sprints 020C and 020E are closed as superseded and cleaned up.
- Sprint 020D is the authority for protected CLI authentication and connectivity to the old project.
- Sprint 020G creates and validates a separate project. It must not reset, delete, drop, repair, replay against, or otherwise clean the old project.
- Old-project decommissioning requires a later separately approved follow-up after cutover acceptance and rollback-retention expiry.

## Security Requirements

- No `SECURITY DEFINER` routine or view may be accepted without reviewed owner, fixed safe search path, minimum execute grants, and justified need.
- Revoke routine execution from `PUBLIC` and `anon` unless a current documented public flow requires it. Grant only exact signatures to the minimum current role(s).
- Preserve current RLS intent but verify every application-owned table has the expected RLS/policy posture.
- Avoid always-true write policies unless explicitly justified by the current repository and protected server-side controls.
- Run Supabase security advisors before migration application review where supported, after build, and after hosted configuration; no unresolved error may remain at cutover.
- Warnings require explicit disposition: fixed, accepted with reason/owner, or blocked.
- Enable leaked-password protection and verify Auth settings before creating production users.

## Migration-History Strategy

The new project starts empty. Apply migrations `0001` onward through the supported Supabase migration workflow so the remote ledger truthfully records each applied version.

Do not:

- copy or fabricate the old project's absent migration ledger
- mark versions applied without executing them on the empty project
- use migration repair to bypass failed SQL
- apply `remote-init.sql` and then separately mark incremental migrations applied
- replay migrations against the old project

If a migration fails, stop. Preserve sanitized error evidence, inspect the new candidate state, and prepare a reviewed forward fix or recreate the still-disposable candidate project only through a separately confirmed recovery step. Never redirect recovery to the old project.

## Data And Fixture Boundary

- New project begins without legacy production rows, Auth users, or Storage objects.
- Repository-supplied deterministic seed/reference rows are allowed.
- Synthetic validation fixtures must be unmistakably synthetic, minimal, owned, timestamped, and cleaned up before production acceptance unless explicitly retained as documented test fixtures.
- Do not use real people, stables, horses, customers, pathology information, email addresses, or uploaded files.
- Auth test accounts must use controlled non-real addresses and an approved operator-managed secret path.

## Cutover Boundary

Cutover changes the application's Supabase endpoint/public key and required server-side credentials to the new project through protected deployment configuration. These are production-impacting external changes expressly included only after all pre-cutover checks pass.

Before cutover record:

- exact old and new project references by safe identifier

- maintenance owner/window
- exact environment scopes to update
- protected secret rotation/re-entry owner
- deployment/restart requirement
- smoke-test owner and checklist

Never print configuration values. After cutover, verify the application points to the new reference by safe hostname/reference only.
