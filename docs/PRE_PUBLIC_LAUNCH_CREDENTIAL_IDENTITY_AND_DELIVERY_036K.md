This internal contract governs exactly seven credential classes, two excluded Supabase Auth identities and one real-trainer normal-delivery rehearsal. It is not a public-launch, legal, customer, representative-acceptance, commerce, enquiry or Product Done claim.

## Credential transaction boundary

The only eligible classes are `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, `ENQUIRY_ABUSE_HMAC_SECRET`, `PUBLIC_ENQUIRY_SMTP_PASS`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `RAILWAY_API_TOKEN`. Public Supabase/Stripe configuration and provider-issued Vercel OIDC are excluded.

For every class, the operator must prove all current and still-addressable immutable/old deployment consumers, provider-native create/install capability, intended-runtime use by the replacement, independent provider-native predecessor invalidation, safe coupling and complete pre-revocation compensation. Vercel row absence, source text, a working replacement or a failed application request never proves provider revocation.

`CRON_SECRET` and `ENQUIRY_ABUSE_HMAC_SECRET` require proof that every addressable consumer rejects or cannot consume the predecessor. SMTP, Stripe and Railway `revoked-not-required` requires exact provider-native revoke/absence plus fail-closed runtime. Supabase service-role rotation must be individually supported and must not rotate public anon configuration, JWT signing authority, sessions or unrelated project keys.

Failure before predecessor revocation removes the replacement and restores the complete affected binding/caller set. Once predecessor invalidation is independently proven, that predecessor is never restored. The verified replacement becomes an accepted retained state; an unsafe post-revocation replacement is a material stop.

Terminal dispositions are exactly `rotated-and-verified`, `revoked-not-required`, `confirmed-inactive-or-absent` and `blocked-retained`. One unsupported matrix cell produces `blocked-retained` and withholds the target outcome.

## Identity disposition boundary

Each excluded identity is privately matched through exact Auth ID plus protected email authority. List position, visible directory rows, counts, partial identifiers and guesses cannot authorize a mutation.

The migration-hash-bound dependency manifest covers migrations `0001`–`0025`, every direct user foreign key, profile/trainer/owner/staff/access and horse-assignment chain, dependent operational/history/biochemistry/evidence records, upload lineage, attempts, holds, audits and exact Storage object joins. Output is limited to table/column class, zero/nonzero and ownership class. Unknown, non-owned, nonzero or unsupported results retain the identity unchanged and block target completion; the sprint does not erase history to manufacture zero.

Installed Supabase Admin global sign-out requires a valid user JWT rather than an Auth ID. Obsolete deletion therefore requires a protected normal target-user session, global sign-out, independent refresh/session-reuse denial, complete zero dependencies, exact-ID Auth deletion last and independent absence. `deleteUser` alone is insufficient. At most one Auth terminal mutation is permitted per excluded ordinal; session and dependency writes are separately bounded.

## Real-trainer private procedure

1. Prove exact accepted source, Ready deployment, five aliases and three binding classes.
2. Prove the trainer identity and one obvious synthetic graph are exact-owned and least-privilege.
3. On one supported phone, the trainer privately enters their own address and requests one normal six-digit sign-in code.
4. The trainer privately submits that code exactly once.
5. The trainer visits the portal, exact synthetic horse and permitted no-submit workflow.
6. A generated wrong horse must return generic unavailable language only.
7. The trainer signs out and proves signed-out and fresh anonymous portal access redirect to sign-in.
8. Exact-owned application/Storage/session/fixture state is removed. A real identity remains only under explicit ongoing-access authority; a rehearsal-created identity otherwise deletes Auth last.

No resend, mailbox automation, generated Admin link, password, service-role authentication substitute or second trainer is permitted. A delivery failure closes safely without retry.

## Phase landing states

The external ledger records phases `0` through `7`: baseline, replacement preparation, install/probe, predecessor invalidation, conditional exact-source redeploy, identity disposition, trainer rehearsal and final readback. State values are exactly `not-started`, `accepted-retained`, `compensated`, `removed`, `revoked-and-invalid`, `unchanged-blocking` and `residue`.

Authorized retained replacement bindings, an accepted candidate and approved continuing real access are not residue. Final proof separately reports staged files, unauthorized external mutations and exact-owned residue. Candidate/alias compensation restores the last compatible deployment and the current verified replacement binding set; it never restores a revoked predecessor or reconstructs a deleted Auth identity.

## Evidence safety and limitations

Credential values, addresses, codes, identities, cookies, JWTs, private rows, provider account content and real horse/stable data stay out of arguments, stdout/stderr, files, screenshots, chat and evidence. Evidence uses class names, ordinals, booleans, counts, route classes and sanitized Brisbane timestamps/durations only.

This sprint does not prove under-60 submission, full representative Sprint 035S acceptance, provider-native restoration, public enquiry, commerce, legal/customer acceptance or Product-wide Done.
